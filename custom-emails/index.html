peakst8 Custom Emails

The club's name on every email.

A club sends its registration emails under its own sender name and address on ps8.in, peakst8's separate domain for club mail, and replaces the subject and design of each email its athletes receive while they register. An email the club has not customised keeps going out in the peakst8 design.

1. The problem

An athlete registers with a club and then hears from peakst8. The club's brand disappears at the moment the athlete commits.

Today
peakst8 Supportsupport@peakst8.clubYour spot is confirmed

Every club, every event: the same sender, the same wording, the same design. A club that wants something different asks an engineer.

With custom emails
Cubbon Run Clubcubbonrunclub@ps8.inYou're in for Sunday Long Run 🎟️

The club sets the sender once and designs each email itself, from its own settings. The club name here is an example.

We have already built one-off branded emails for single events by hand. Each costs engineering time and leaves a special case in the code. This replaces that with something a host does themselves.

2. What ships

A new Emails tab in the club's settings, with a sender and a list of emails the club can redesign.

1 · Sender nameWho it's from

The name athletes see in their inbox, for example "Cubbon Run Club".

2 · Sender addressBefore the @

The host picks the first part. The address is always on ps8.in.

3 · Email listOne per moment

Each email peakst8 sends during a registration, marked Default or Custom.

4 · Custom HTMLSubject and design

The host pastes their own HTML and, if they want, their own subject line.

5 · Preview and resetSee it, undo it

A preview of the design, and one click back to the peakst8 default.

Not in this version: sending from the club's own domain, a drag-and-drop builder, a different design per event, marketing emails, and sending a test email to yourself.

4. How it works

At send time peakst8 looks up the club that owns the event and uses whatever the club has set, piece by piece. Anything not set falls back to the peakst8 default.

  1. A registration moment happens for an event: a code is requested, or a ticket is issued.
  2. peakst8 finds the owning club's email settings and its newest design for that email type.
  3. Each piece is chosen on its own: sender name, sender address, subject, HTML. A club with a sender but no design gets its own sender on the peakst8 design. A design saved with a blank subject gets the default subject.
  4. Variables are filled in for that athlete, in the subject and the body.
  5. The email joins the same send queue as every other peakst8 email, so pacing, retries and the send log are unchanged.

If the lookup of the club's settings fails, the email goes out in the peakst8 design. A branding problem never holds up a code or a ticket.

5. Rules

  • The domain is fixed (ps8.in once the move ships; peakst8.club in the current build). The host types only the part before the @. It may contain letters, digits, ., - and _, is stored in lower case, and is at most 64 characters. The sender name is at most 100 characters.
  • Required variables are enforced on save. A design missing one is refused, and the message names the missing variables.
  • A subject is optional and at most 200 characters. Blank means the default subject.
  • One design per email type per club. It applies to every event of that club. Saving again replaces it.
  • Reset deletes the club's design for that email type, and the default is sent from the next email on.
  • The HTML is stored as the host wrote it. It is only ever mailed, and the preview renders it in a locked frame with scripts and forms switched off.
  • The preview shows variables as written, for example {{ otp }}, the same for every email. No sample values.
  • Only a host who belongs to the club can see or change its email settings.
  • Campaign emails are not affected. founders peak and Project 3 events keep their own confirmation designs.

6. A separate domain for club mail (planned)

Not built yet. Today a club's sender address is on peakst8.club, the domain peakst8's own emails use. Before clubs go live it moves to ps8.in.

Default emails
peakst8 Supportsupport@peakst8.club

A club that has customised nothing. Unchanged.

Custom emails
Cubbon Run Clubcubbonrunclub@ps8.in

A club's own sender and designs go out from the separate domain.

Why: inbox providers such as Gmail judge a sending domain by the mail that comes from it. If a club's design or wording gets marked as spam, that counts against the whole domain. Keeping club mail on ps8.in means it cannot hurt delivery of peakst8's own login codes and tickets.

Build notes

  • Domain setup: verify ps8.in for sending with the email provider (SES), with DKIM, SPF and a DMARC record. Until that is done, mail from it is rejected or lands in spam.
  • Code: the club sender is built on ORGANIZATION_EMAIL_DOMAIN (peakst8.club) today. Add a separate constant for the club mail domain and use it where the club's address is saved; the default sender keeps the existing one.
  • Sending: the mail server login does not change, only the From header. Confirm the provider accepts ps8.in as a From domain on that login.
  • Existing rows: sender addresses already saved on peakst8.club are moved to ps8.in, keeping the part before the @.
  • Screens: the address field's fixed suffix becomes @ps8.in.
  • Warm-up: a new domain has no track record. Start with low volumes and check where test mail lands in Gmail and Outlook.

Open: a club that set its own sender but kept the peakst8 design. Proposed: it sends from ps8.in, since the sender is the club.

7. Consent and opt-out (planned)

Not built yet. Once clubs write their own emails, we need to show that an athlete agreed to receive them and can stop them. The deadline is the Indian data protection law's consent rules, which apply from about 13 May 2027.

1 · Opt-in checkboxOn the registration form

Unticked by default, apart from the terms and waiver tick. Says who will email the athlete (the club and peakst8) and about what.

2 · Saved for goodWho agreed to what

When the athlete ticked it, for which club, and the wording they saw.

3 · Opt-out buttonIn the emails

One click, no login, effective straight away. As easy as opting in.

4 · Respected at sendNo optional mail

An athlete who opted out stops getting that club's optional emails.

The law

  • The Digital Personal Data Protection Act, 2023 (DPDP Act), section 6: consent must be free, specific, informed, unconditional and unambiguous, given by a clear affirmative action. A pre-ticked box or silence does not count.
  • The same section lets a person withdraw consent at any time, says withdrawing must be as easy as giving it, and requires us to stop within a reasonable time.
  • The DPDP Rules were notified on 13 November 2025. The consent obligations start applying 18 months later, around 13 May 2027 (government notification).
  • India has no email-specific law like the US CAN-SPAM Act, and the Act does not mention email or unsubscribe links. An unsubscribe button is the practical way to meet the "as easy to withdraw" rule (commentary).

This is our reading of the Act and of published commentary, not legal advice. A lawyer should confirm it before we build.

Build notes (proposal)

  • Record every change: each opt-in and opt-out is saved in the database as a new row and never edited or deleted by the product, so we can answer a complaint or a regulator with exactly what was agreed and when. See the table below.
  • Registration form: a new checkbox, separate from acceptedParticipationTermsAndWaiver, stored with a timestamp and the consent wording shown.
  • Opt-out link: a signed link per athlete and club, so it works without a login and cannot be guessed. It opens a page that confirms the opt-out and offers to undo it.
  • Custom designs: the opt-out link becomes a required variable for optional emails, checked on save like the others, so a club's design cannot leave it out.
  • Sending: the check happens where the email is queued, so every optional email obeys it without each caller remembering to.
  • Hosts: an opted-out athlete is still registered and still appears in the club's registration list.

What we save (proposal)

One table of consent events, written to on every opt-in and opt-out. The athlete's current state is their latest row for that club.

  • Append only: no update or delete path in the code. A re-opt-in is a new row.
  • Declines are rows too, so "never asked" and "asked and said no" are different.
  • Email kept as a snapshot, because an athlete can change their address later and the record must show where the mail was going.
  • Retention and account deletion: an open question for the lawyer. The record may need to outlive the account so we can prove the consent existed.
  • No IP address or device details are proposed. Add them only if the lawyer asks for them, since they are personal data too.

9. Design brief

The Emails tab is built and working. These are the states a designer should cover when refining it.

  • Sender: name field, address field with a fixed @ps8.in suffix, saved state, and the error when the address has a character that is not allowed.
  • Email list: each email's name, a one-line description of when it is sent, and a Default or Custom tag. The list will grow, so it should scan well at ten or more rows.
  • Editor: Default / Custom HTML switch, subject field showing the default as placeholder, HTML field, the row of required variables, and the error naming missing variables.
  • Preview: subject line above a white email frame, variables shown as written. A variable used as an image source, such as the QR code, shows as a broken image here; decide whether to draw a placeholder instead.
  • Reset: a clear way back to the default, with a confirmation, since it deletes the club's design.
  • Empty and loading states for a club that has never opened the tab.

How we test

  • On staging, with a test club: set a sender, register for a free event and a paid event, and check both emails arrive from the club's sender.
  • Custom design: save a design for each email, register again, and check every variable is filled in, in the subject and the body.
  • Guard: try to save a design with a required variable removed and confirm it is refused.
  • Fallback: reset to default and confirm the peakst8 design returns; register with a club that has no settings and confirm nothing changed.
  • Inboxes: open each email in Gmail, Outlook and Apple Mail, on a phone and a laptop.
  • Squad: confirm a squad member's confirmation uses the club's design and the captain's QR code.
